# Что происходит при выборе ADMX-политики, изменении состояния и нажатии "Применить"

## Цель

Описать текущий рабочий сценарий ADMX в `chain/js/app.js`:

1. пользователь выбирает политику
2. политика загружается в UI
3. пользователь меняет состояние
4. пользователь нажимает `Применить`
5. фронт читает и сохраняет данные через `API.js`

## 1. Что происходит при выборе политики

### 1.1. Политика уже есть в дереве

До выбора политика уже загружена в дерево через:

- `API.loadMainPolicy()` -> `API.getPolicy("/")`

На основе ответа строится дерево политик в `buildTreeViewList()` и `convertPolicyCategory()`.

Для каждой ADMX-политики в item сохраняются:

- `policyKey`
- `policyData`
- `template: "admx"`
- `admxTreePath`
- `target`

Где:

- `admxTreePath` это путь политики в дереве, например `Machine/categories/.../policies`
- `target` это `"Machine"` или `"User"`

Это делается в `chain/js/app.js`:

- `convertPolicyCategory()`

### 1.2. При клике по политике вызывается рендер ADMX

Когда пользователь выбирает узел дерева:

- `treeViewState.renderSelectedItem(item, element)` определяет тип элемента
- если `item.template === "admx"`, вызывается `renderAdmxTemplate(...)`

Это происходит в:

- `renderSelectedItem()`
- `renderAdmxTemplate()`

## 2. Что делает renderAdmxTemplate()

После открытия ADMX-политики `renderAdmxTemplate()` делает несколько шагов.

### 2.1. Разбирает описание политики

Из `item.policyData` берутся:

- `policyHeader`
- `controlEntries`
- `policyValueEntry`

Для этого используется:

- `normalizePolicyEntries(policyData, policyHeader)`

Результат:

- `policyValueEntry` описывает состояние политики
- `controlEntries` описывают контролы внутри политики

### 2.2. Строит DOM формы

Форма включает:

- заголовок политики
- radio-кнопки состояния:
  - `not-configured`
  - `enabled`
  - `disabled`
- список контролов политики
- help-блок
- статусный блок `gp__admx-status`

В этот момент контролы создаются disabled.

### 2.3. Готовит служебное состояние формы

Внутри `renderAdmxTemplate()` создаются переменные:

- `initialFormSnapshot`
- `currentMetadata`
- `isLoading`
- `isSaving`
- `hasLoadError`

Они используются для:

- отслеживания измененности формы
- блокировки `Apply/Cancel`
- загрузки текущего server state
- сохранения политики

## 3. Что происходит сразу после открытия политики

После создания формы автоматически запускается загрузка текущего значения политики с backend.

### 3.1. Загружается name_gpt

Для вызовов backend нужен `name_gpt`.

Он получается раньше, в `init()`:

- если есть `options.policyName`
- вызывается `gpo.show`
- из ответа берется `gpcfilesyspath`
- значение нормализуется в строку

Функции:

- `waitForNameGpt()`
- `normalizeSingleString()`

Итог:

- `waitForNameGpt()` возвращает путь до GPO в виде строки

### 3.2. Загружается metadata для set_policy

Вызов:

- `resolveAdmxMetadata(admxTreePath)`

Что делает функция:

1. вызывает `API.getPolicy(admxTreePath)`
2. обходит ответ рекурсивно
3. ищет строку вида `Read_Path_GPT('...')`
4. извлекает внутренний путь

Пример результата:

- `Software\\BaseALT\\Policies\\Control\\xdg-user-dirs`

Этот путь потом используется как `metadata` в `API.setPolicy(...)`.

### 3.3. Загружается текущее состояние политики

Вызов:

- `loadAdmxStateFromApi({ target, admxTreePath })`

Что делает функция:

1. ждет `name_gpt` через `waitForNameGpt()`
2. проверяет `target`
3. проверяет `admxTreePath`
4. параллельно вызывает:
   - `resolveAdmxMetadata(admxTreePath)`
   - `API.getCurrentValue(nameGpt, target, admxTreePath)`

Возвращает:

- `nameGpt`
- `metadata`
- `apiState`

### 3.4. Разбирается ответ get_current_value

Ответ backend обрабатывается в:

- `parseAdmxCurrentValue(rawValue)`

Эта функция:

- умеет разбирать строку JSON
- умеет разбирать вложенные структуры
- умеет проходить через массивы
- пытается найти полезные данные в:
  - `value`
  - `values`
  - `currentValue`
  - `policyValue`
  - `result`

Если найден объект со `state`, он считается валидным состоянием политики.

### 3.5. Состояние применяется к форме

Вызов:

- `applyAdmxApiState({ rootElement, apiState, controlEntries })`

Что делает:

1. берет `apiState.state`
2. устанавливает radio-кнопку через `setSelectedAdmxState()`
3. пытается заполнить значения контролов
4. вызывает `syncControlsWithPolicyState(rootElement)`

Важно:

- если состояние `enabled`, контролы становятся доступными
- если состояние не `enabled`, контролы остаются disabled

### 3.6. Фиксируется исходный snapshot

После успешной загрузки выполняется:

- `buildAdmxFormSnapshot({ rootElement, controlEntries })`

Snapshot нужен для:

- определения, изменилась ли форма
- работы кнопки `Cancel`
- отключения `Apply`, если изменений нет

## 4. Что происходит, когда пользователь меняет состояние политики

Когда пользователь переключает radio-кнопку состояния:

- срабатывает `handleStatePolicyChange`

Он делает:

1. проверяет, что изменился именно `input[name="admx-state"]`
2. вызывает `syncControlsWithPolicyState(admxTemplateElement)`
3. вызывает `refreshHeaderAdmxButtons()`

### 4.1. Что делает syncControlsWithPolicyState()

Функция:

- читает текущее состояние через `getSelectedAdmxState(rootElement)`
- если состояние не `enabled`, отключает контролы
- если состояние `enabled`, включает контролы

### 4.2. Что делает refreshHeaderAdmxButtons()

Функция:

1. строит текущий snapshot формы
2. сравнивает его с `initialFormSnapshot`
3. если есть различия, делает активными:
   - `admx__btn-apply`
   - `admx__btn-cancel`

Именно поэтому после смены состояния кнопка `Применить` становится active.

## 5. Что происходит при нажатии "Применить"

Обработчик:

- `handleApply`

Он запускается по клику на:

- `.admx__btn-apply`

### 5.1. Первичная проверка

`handleApply` сначала проверяет:

- кнопка действительно active
- форма не в состоянии `isLoading`
- форма не в состоянии `isSaving`
- нет `hasLoadError`

Если одно из условий не выполнено, сохранение не идет.

### 5.2. Форма переводится в режим сохранения

Сразу после старта:

- `isSaving = true`
- `setStatusMessage("Сохранение политики...")`
- `setHeaderAdmxButtonsActive(false)`
- `setAdmxFormDisabledState(true)`

Итог:

- кнопки `Apply/Cancel` блокируются
- поля формы временно блокируются

### 5.3. Проверяются обязательные данные

Дальше `handleApply` проверяет:

- `currentNameGpt`
- `effectiveTarget`
- `effectiveAdmxTreePath`

Если чего-то не хватает, выбрасывается ошибка.

### 5.4. При необходимости догружается metadata

Если `currentMetadata` еще не определено:

- вызывается `resolveAdmxMetadata(effectiveAdmxTreePath)`

### 5.5. Собирается payload политики

Вызов:

- `buildAdmxPolicyPayload({ rootElement, controlEntries })`

Что делает:

1. берет текущее состояние через `getSelectedAdmxState()`
2. проходит по всем `controlEntries`
3. считывает значения через `readControlValue()`
4. собирает объект:

```json
{
  "state": "enabled",
  "values": {
    "...": "..."
  }
}
```

5. сериализует его в строку через `JSON.stringify(...)`

Это и есть `jsonData`, который отправляется в backend.

### 5.6. Дополнительно собирается optimistic state

Вызов:

- `buildCurrentAdmxApiState({ rootElement, controlEntries })`

Это локальный слепок текущей формы:

- текущее `state`
- текущие `values`

Он нужен на случай, если backend после сохранения вернет ответ, который фронт не сможет корректно распознать.

### 5.7. Выполняется сохранение через API.js

Главный вызов:

- `API.setPolicy(currentNameGpt, effectiveTarget, effectiveAdmxTreePath, jsonData, currentMetadata)`

Аргументы:

- `currentNameGpt` — путь до GPO
- `effectiveTarget` — `Machine` или `User`
- `effectiveAdmxTreePath` — путь политики
- `jsonData` — строка JSON
- `currentMetadata` — извлеченный путь из `Read_Path_GPT('...')`

Внутри `API.js` это уходит в RPC:

- `gpo.set_policy`

## 6. Что происходит после успешного setPolicy

После сохранения фронт не заканчивает работу сразу.

Он делает повторное чтение текущего состояния политики:

- `loadAdmxStateFromApi({ target, admxTreePath })`

То есть:

1. снова читает backend
2. получает `apiState`
3. пытается синхронизировать UI с тем, что реально хранится на сервере

### 6.1. Если backend вернул понятный ответ

Если `hasUsableAdmxApiState(reloadedState.apiState)` возвращает `true`:

- вызывается `applyAdmxApiState(...)`
- форма обновляется server state
- строится новый `initialFormSnapshot`
- кнопка `Apply` снова становится неактивной
- статус очищается

Это означает:

- форма и сервер синхронизированы

### 6.2. Если backend вернул непонятный ответ

Если backend после сохранения вернул ответ, который нельзя надежно распарсить:

- в консоль пишется предупреждение
- используется optimistic fallback

То есть:

- `applyAdmxApiState(...)` вызывается не с ответом backend, а с локальным `optimisticApiState`
- snapshot обновляется на основании текущей формы
- статус показывает сообщение:
  - `Политика сохранена, но ответ backend не удалось полностью распознать.`

Это сделано, чтобы форма не сбрасывалась визуально обратно в `not-configured` только из-за того, что post-save ответ backend пришел в нестандартном формате.

## 7. Что происходит при ошибке сохранения

Если внутри `handleApply` возникает ошибка:

- пишется `console.error("[ADMX] Failed to save policy.", error)`
- в статус выводится:
  - `Не удалось сохранить политику.`

После этого:

- `isSaving = false`
- форма снова разблокируется
- `refreshHeaderAdmxButtons()` пересчитывает состояние кнопок

Важно:

- `initialFormSnapshot` в случае ошибки не обновляется
- это значит, что форма по-прежнему считается измененной
- пользователь может попробовать `Применить` еще раз

## 8. Что происходит при нажатии "Отмена"

Если `Cancel` активна:

- вызывается `applyAdmxFormSnapshot(...)`

Что делает:

1. восстанавливает сохраненный `initialFormSnapshot`
2. возвращает исходное `state`
3. возвращает исходные значения контролов
4. вызывает `syncControlsWithPolicyState()`

После этого:

- статус очищается
- `Apply/Cancel` снова деактивируются

## 9. Краткая схема сценария

### Выбор политики

1. Пользователь выбирает ADMX-политику в дереве.
2. `renderSelectedItem()` вызывает `renderAdmxTemplate()`.
3. Форма строится на основе `policyData`.
4. Фронт загружает:
   - `name_gpt`
   - `metadata`
   - текущее состояние через `API.getCurrentValue()`
5. Ответ backend применяется к форме.
6. Фиксируется `initialFormSnapshot`.

### Изменение состояния

1. Пользователь меняет `admx-state`.
2. `handleStatePolicyChange` обновляет доступность контролов.
3. `refreshHeaderAdmxButtons()` сравнивает snapshot.
4. `Apply` становится active.

### Нажатие "Применить"

1. `handleApply` блокирует форму.
2. Собирается `jsonData`.
3. Вызывается `API.setPolicy(...)`.
4. После этого фронт повторно вызывает `API.getCurrentValue(...)`.
5. Если backend-ответ понятен:
   - форма синхронизируется с backend
6. Если backend-ответ непонятен:
   - сохраняется optimistic UI state
7. Обновляется snapshot.
8. Кнопка `Apply` перестает быть active.

## 10. Итог

На текущий момент сценарий работает так:

- выбор политики открывает ADMX-форму и грузит server state
- изменение состояния активирует `Apply`
- `Apply` сохраняет политику через `API.setPolicy(...)`
- затем фронт пытается перечитать состояние через `API.getCurrentValue(...)`
- если backend-ответ читается нормально, UI показывает серверное состояние
- если backend-ответ после сохранения не читается, UI остается в optimistic state и не откатывает форму назад

Таким образом, кнопка `Применить` теперь выполняет не локальное сохранение, а серверную операцию с последующей синхронизацией формы.
