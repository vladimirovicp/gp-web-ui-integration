# ADMX: состояния политики и жизненный цикл формы

Дата: `2026-05-25`

## Цель документа

Этот документ описывает, как в текущей реализации UI работает ADMX-политика в трех состояниях:

- `Не сконфигурировано` (`not-configured`)
- `Включено` (`enabled`)
- `Отключено` (`disabled`)

Также документ фиксирует поведение:

- при открытии ADMX-политики;
- при загрузке текущих значений с сервера;
- при изменении состояния политики;
- при сохранении через `Применить`;
- при откате через `Отмена`;
- при повторном открытии политики или переключении на другой узел.

## Где находится логика

Основные модули:

- `chain/js/components/templates/admx-template.js`
- `chain/js/components/templates/admx/admx-template-controller.js`
- `chain/js/components/templates/admx/admx-form-state.js`
- `chain/js/components/templates/admx/admx-value-parser.js`
- `chain/js/components/templates/admx/admx-policy-normalizers.js`
- `chain/js/components/templates/admx/admx-controls-renderer.js`

Связанные внешние точки:

- `chain/js/app.js` — открывает ADMX-шаблон и вызывает `cleanup()` при переключении
- `chain/js/components/header/header.js` — содержит кнопки `Применить` и `Отмена`
- `chain/js/util/API` — используется для `API.get_current_value`, `API.set`, `API.deletePolicy`, `API.waitForNameGpt`

## Краткий итог поведения

В текущей реализации ADMX работает так:

- при открытии значения загружаются только с сервера через `API.get_current_value`;
- если сервер не вернул данные, форма переводится в `Не сконфигурировано` и заполняется дефолтами;
- при `Включено` контролы редактируемы;
- при `Отключено` и `Не сконфигурировано` контролы заблокированы;
- `Применить` для `enabled` и `disabled` вызывает `API.set`;
- `Применить` для `not-configured` вызывает `API.deletePolicy`;
- `Отмена` возвращает форму к последнему загруженному или успешно сохраненному snapshot;
- никаких fallback в `localStorage` больше нет.

## 1. Что считается состоянием политики

Состояния заданы в `admx-constants.js`:

- `not-configured`
- `enabled`
- `disabled`

Состояние по умолчанию:

```js
const ADMX_DEFAULT_STATE = 'not-configured';
```

Любое неизвестное состояние нормализуется в `not-configured`.

## 2. Что рендерится при открытии ADMX

При открытии файла с `template === 'admx'` приложение вызывает `renderAdmxTemplate(...)`.

На экране создаются:

- заголовок политики;
- блок `Состояние политики` с тремя radio-кнопками;
- список ADMX-контролов;
- help-блок;
- привязка контроллера, который управляет загрузкой, сохранением и dirty-checking.

Начальный DOM создается так:

- `Не сконфигурировано` отмечено по умолчанию;
- все ADMX-контролы рендерятся в disabled-состоянии;
- кнопки `Применить` и `Отмена` не должны быть активны до окончания загрузки.

Это значит, что первичный UI всегда стартует в безопасном нейтральном состоянии, а затем уже обновляется по ответу API.

## 3. Как определяется набор контролов и путей

Перед запуском контроллера вызывается `normalizePolicyEntries(policyData, policyHeader)`.

Эта функция делит данные политики на:

- `controlEntries` — реальные поля формы (`enum`, `boolean`, `decimal`, `text`);
- `policyValueEntry` — служебную запись типа `policyValue`.

Для каждого контрола рассчитываются:

- `policyPath` — путь политики для работы с API;
- `storagePath` — путь, по которому контрол затем ищется в DOM и читается/записывается.

Если в `data` есть `Read_Path_GPT('...')`, то именно этот путь становится `storagePath`.

## 4. Что происходит при открытии политики

После рендера `setupAdmxTemplateController(...)` сразу запускает `loadCurrentAdmxValues()`.

Порядок такой:

1. Получается текущий `nameGpt` через `API.waitForNameGpt()`.
2. Проверяется наличие `effectiveTarget`.
3. Для каждого ADMX-контрола вызывается `API.get_current_value(nameGpt, effectiveTarget, controlPath)`.
4. Каждый ответ парсится через `parseAdmxCurrentValue(...)`.
5. На основании результатов форма либо заполняется серверными данными, либо переводится в дефолтное состояние.
6. После завершения загрузки строится `initialFormSnapshot`.

Пока идет загрузка:

- изменения пользователя не обрабатываются;
- `Apply/Cancel` не должны становиться активными.

## 5. Как интерпретируется ответ `API.get_current_value`

Парсер понимает несколько форматов ответа.

### Пустое значение

Следующие случаи считаются отсутствием данных:

- `null`
- `undefined`
- пустая строка
- пустой объект `{}`
- пустой массив или массив без полезного значения

В этом случае результат нормализуется как:

```js
{
  hasData: false,
  state: 'not-configured',
  value: null
}
```

### Строковый формат

Актуальный строковый формат:

- `**DeleteValues` означает состояние `disabled`;
- любая другая непустая строка без служебного префикса означает состояние `enabled`, а сама строка считается значением контрола.

Примеры:

- `abc` => `enabled`, значение `abc`;
- `42` => `enabled`, значение `42`;
- `trueValue` => `enabled`, значение `trueValue`;
- `**DeleteValues` => `disabled`, значение контрола не используется.

Для обратной совместимости парсер также понимает старый формат:

```text
enabled;VALUE
disabled;VALUE
not-configured;VALUE
```

В этом случае:

- часть до `;` трактуется как состояние;
- часть после `;` трактуется как значение контрола.

Если в старом формате пришло `disabled;VALUE`, политика считается `disabled`, но форма заполняется дефолтными значениями по новой логике.

### Объектный формат

Если сервер возвращает объект:

- с `value_data`, то парсится `value_data`;
- с `state`, то берется `state` и поле `value`;
- с `result`, `value` или `currentValue`, вложенность сначала раскрывается рекурсивно.

## 6. Как форма выбирает итоговое состояние после загрузки

После получения данных по всем контролам контроллер:

- берет результат первого контрола как источник состояния политики;
- проверяет, есть ли вообще хотя бы один контрол с `hasData: true`.

Дальше есть два сценария.

### Если сервер ничего не вернул ни по одному контролу

Вызывается `applyDefaultValuesToAdmxForm(...)`.

Это означает:

- состояние формы ставится в `Не сконфигурировано`;
- каждому контролу присваивается дефолтное значение;
- все контролы блокируются.

### Если хотя бы по одному контролу есть данные

Тогда:

- состояние формы выставляется из `firstValue.state`;
- если состояние `enabled`, каждый контрол получает серверное значение, если оно есть;
- если состояние `enabled`, но по конкретному контролу данных нет, он получает свое дефолтное значение;
- если состояние `disabled`, все контролы получают дефолтные значения независимо от служебного значения сервера;
- затем вызывается `syncControlsWithPolicyState(...)`.

## 7. Поведение состояний политики

### 7.1 `Не сконфигурировано`

Смысл состояния:

- политика считается отсутствующей в конфигурации;
- в UI это дефолтное состояние;
- при сохранении используется удаление, а не запись значения.

Поведение формы:

- radio `Не сконфигурировано` выбран;
- все контролы disabled;
- в самих контролах лежат дефолтные значения, но они не считаются сохраненной политикой.

Что происходит при `Применить`:

- для каждого `controlEntry` вызывается `API.deletePolicy(nameGpt, effectiveTarget, controlPath)`;
- после успешного завершения форма повторно сбрасывается в дефолты через `applyDefaultValuesToAdmxForm(...)`;
- новый `initialFormSnapshot` строится уже из дефолтного состояния.

Итог:

- серверные записи политики удаляются;
- UI остается в `Не сконфигурировано`;
- `Apply/Cancel` снова становятся неактивными, если после этого пользователь ничего не менял.

### 7.2 `Включено`

Смысл состояния:

- политика активна;
- значения контролов становятся значимыми и доступны для редактирования.

Поведение формы:

- radio `Включено` выбран;
- все контролы становятся доступными для ввода;
- пользователь может менять значения полей.

Что происходит при `Применить`:

- для каждого контрола читается текущее значение через `readControlValue(...)`;
- через `buildAdmxSetValue(...)` формируется само значение контрола без префикса состояния;
- вызывается `API.set(nameGpt, effectiveTarget, controlPath, setValue)`.

Примеры сериализации:

- текст: `abc`
- число: `42`
- булево значение: `trueValue` или `falseValue`
- enum: `selectedKey`

Ключевой момент:

- наличие обычного значения на сервере означает, что политика находится в состоянии `enabled`;
- префикс `enabled;` больше не записывается.

После успешного сохранения:

- текущая форма становится новым `initialFormSnapshot`;
- кнопки `Apply/Cancel` деактивируются.

### 7.3 `Отключено`

Смысл состояния:

- политика присутствует, но установлена в disabled-состояние.

Поведение формы:

- radio `Отключено` выбран;
- все контролы disabled;
- пользователь не может менять значения полей, пока не переключит состояние в `Включено`.

Что происходит при `Применить`:

- значение контрола не используется как полезная нагрузка;
- формируется служебная строка `**DeleteValues`;
- вызывается `API.set(...)`, а не `API.deletePolicy(...)`.
- после успешного сохранения контролы сбрасываются к дефолтным значениям;
- новый `initialFormSnapshot` строится уже из состояния `disabled` с дефолтными значениями.

Ключевой момент:

- `Отключено` в текущей реализации означает сохраненную запись со служебным значением `**DeleteValues`;
- это не то же самое, что `Не сконфигурировано`.

Разница:

- `Отключено` => запись существует, используется `API.set("**DeleteValues")`
- `Не сконфигурировано` => запись удаляется, используется `API.deletePolicy`

## 8. Почему контролы заблокированы в `disabled` и `not-configured`

Функция `syncControlsWithPolicyState(rootElement)` делает очень простое правило:

```js
setControlsDisabledState(rootElement, currentState !== 'enabled');
```

Следствие:

- только `enabled` делает поля редактируемыми;
- `disabled` и `not-configured` ведут себя одинаково в части доступности контролов;
- различие между ними проявляется не в UI-доступности, а в типе RPC при сохранении.

## 9. Дефолтные значения контролов

Когда форма сбрасывается в дефолтное состояние, значения берутся из `getDefaultControlValue(metadata)`.

Правила:

- `enum` — `defaultItem`, а если его нет, первый элемент списка;
- `boolean` — `falseValue`, если он задан, иначе `false`;
- `decimal` — `metadata.defaultValue`, иначе пустая строка;
- `text` — `metadata.defaultValue`, иначе пустая строка.

Важно:

- эти значения используются как стартовые и fallback-значения формы;
- сами по себе они не означают, что политика сохранена на сервере.

## 10. Как работают `Apply` и `Cancel`

Логика основана на snapshot формы.

Snapshot содержит:

- текущее состояние политики;
- массив значений всех контролов.

Формат по сути такой:

```js
{
  state: 'enabled' | 'disabled' | 'not-configured',
  controls: [
    { path, type, value },
    ...
  ]
}
```

### Когда создается `initialFormSnapshot`

Он строится:

- после завершения первичной загрузки;
- после успешного `Apply`;
- после сброса в `not-configured`, когда удаление прошло успешно.

### Когда `Apply/Cancel` становятся активными

После любого изменения контроллер строит текущий snapshot и сравнивает его с `initialFormSnapshot` через:

```js
JSON.stringify(currentSnapshot) !== JSON.stringify(initialFormSnapshot)
```

Если snapshots отличаются:

- кнопка `Применить` активна;
- кнопка `Отмена` активна.

Если snapshots равны:

- обе кнопки неактивны.

### Что делает `Отмена`

`Cancel` не обращается к серверу.

Он:

- берет `initialFormSnapshot`;
- восстанавливает состояние radio;
- восстанавливает значения всех контролов;
- повторно синхронизирует disabled/enabled статус контролов.

То есть `Отмена` возвращает форму к:

- последнему загруженному с сервера состоянию;
- или последнему успешно сохраненному состоянию.

## 11. Что происходит при сохранении

Алгоритм `handleApply()`:

1. Проверяется, что `Apply` активна и нет `isLoading/isSaving`.
2. Получается `nameGpt`.
3. Читается текущее состояние политики.
4. Для каждого ADMX-контрола выполняется одна из веток:
   - `not-configured` => `API.deletePolicy(...)`
   - `enabled` => `API.set(...)` со значением контрола без префикса состояния
   - `disabled` => `API.set(...)` со значением `**DeleteValues`
5. Если все запросы успешны, обновляется `initialFormSnapshot`.
6. Если состояние было `not-configured`, форма дополнительно принудительно сбрасывается в дефолты и остается в `not-configured`.
7. Если состояние было `disabled`, контролы сбрасываются в дефолты и форма остается в `disabled`.
8. После завершения снова пересчитывается активность кнопок.

Запросы по всем контролам уходят параллельно через `Promise.all(...)`.

## 12. Что происходит при ошибке

### Ошибка загрузки

Если чтение текущих значений завершилось ошибкой:

- ошибка логируется в консоль;
- форма переводится в дефолтное состояние через `applyDefaultValuesToAdmxForm(...)`;
- после этого все равно формируется `initialFormSnapshot`.

Итог для пользователя:

- UI открывается;
- состояние будет `Не сконфигурировано`;
- поля будут заполнены дефолтами и заблокированы.

### Ошибка сохранения

Если в `handleApply()` возникает ошибка:

- ошибка логируется в консоль;
- `initialFormSnapshot` не обновляется;
- форма остается в текущем пользовательском состоянии;
- после выхода из `finally` кнопки будут пересчитаны заново.

Обычно это означает, что несохраненные изменения останутся видимыми, и пользователь сможет повторить `Применить`.

## 13. Что происходит при повторном открытии политики

При повторном открытии ADMX-политики:

- старый view сначала очищается через `cleanupCurrentView()` в `app.js`;
- если текущий шаблон ADMX имел `cleanup()`, снимаются его event listeners;
- новая форма создается заново;
- затем снова запускается `loadCurrentAdmxValues()`;
- состояние снова читается только с сервера.

Это означает:

- несохраненные изменения не переживают повторное открытие;
- после переключения на другой узел и возврата форма не восстанавливается из браузерного хранилища;
- источник истины при открытии всегда серверный ответ.

## 14. Практический сценарий по шагам

### Сценарий 1. На сервере нет данных

1. Пользователь открывает ADMX-политику.
2. `API.get_current_value` не возвращает полезных данных.
3. Форма становится `Не сконфигурировано`.
4. Контролы получают дефолты и блокируются.
5. `Apply/Cancel` неактивны.

### Сценарий 2. На сервере сохранено `enabled`

1. Политика открывается.
2. API возвращает, например, `5`.
3. Radio переключается в `Включено`.
4. Контролы заполняются серверными значениями.
5. Контролы становятся доступными для редактирования.
6. После изменения любого поля активируются `Apply/Cancel`.

### Сценарий 3. На сервере сохранено `disabled`

1. Политика открывается.
2. API возвращает `**DeleteValues`.
3. Radio переключается в `Отключено`.
4. Контролы заполняются дефолтными значениями.
5. Контролы остаются заблокированными.
6. Для редактирования пользователь должен переключить состояние в `Включено`.

### Сценарий 4. Пользователь ставит `Не сконфигурировано` и сохраняет

1. Пользователь выбирает `Не сконфигурировано`.
2. Контролы блокируются.
3. Нажимает `Применить`.
4. По каждому пути вызывается `API.deletePolicy(...)`.
5. После успеха форма сбрасывается к дефолтам.
6. Новый базовый snapshot соответствует `not-configured`.

## 15. Важные особенности текущей реализации

### Состояние берется из первого результата с данными

При загрузке итоговое состояние политики берется из первого ответа, где есть полезные данные:

- `const firstValueWithData = results.find(({ parsedValue }) => parsedValue?.hasData)?.parsedValue ?? null;`

Это означает, что пустой ответ по первому пути не мешает корректно распознать `enabled` или `disabled` по следующему пути.

Если сервер вернет несогласованные состояния по разным путям, UI будет ориентироваться на первый путь, где состояние реально удалось прочитать.

### `policyValueEntry` сейчас не участвует в сохранении

`policyValueEntry` нормализуется и его метаданные пробрасываются в DOM как data-атрибуты блока состояния, но в текущем контроллере сохранение выполняется только по `controlEntries`.

Практически это значит:

- реальное чтение и запись опираются на пути обычных ADMX-контролов;
- состояние политики выводится из значения каждого контрола: обычное значение означает `enabled`, `**DeleteValues` означает `disabled`.

### `disabled` сохраняет служебный маркер, а не значение контрола

Когда состояние `Отключено`, код вызывает `API.set(...)` с payload:

```text
**DeleteValues
```

Значения контролов при этом не сохраняются. При следующей загрузке `**DeleteValues` снова будет интерпретирован как `disabled`, а форма будет показана с дефолтными значениями.

## 16. Итоговая модель работы

Текущую реализацию можно описать так:

- сервер является единственным источником данных при открытии;
- форма всегда имеет одно из трех состояний: `not-configured`, `enabled`, `disabled`;
- редактирование значений разрешено только для `enabled`;
- `not-configured` удаляет политику;
- `enabled` сохраняет только значение контрола без префикса состояния;
- `disabled` сохраняет политику в отключенном состоянии через `**DeleteValues`;
- `Cancel` работает только локально через snapshot;
- после успешного сохранения текущая форма становится новой базовой точкой сравнения.

## 17. Короткая таблица различий состояний

| Состояние | Контролы | Сохранение | Смысл |
|-----------|----------|------------|-------|
| `Не сконфигурировано` | disabled | `API.deletePolicy` | Политика удаляется |
| `Включено` | enabled | `API.set("value")` | Политика активна |
| `Отключено` | disabled | `API.set("**DeleteValues")` | Политика сохранена как disabled |
