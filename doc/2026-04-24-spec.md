# Спецификация миграции ADMX с LocalStorage на API.js

## Документ

- Дата: 2026-04-24
- Основание: анализ кода в папке `chain` и отчет `doc/2026-04-24.md`
- Решение: полностью убрать `localStorage` из ADMX-контура
- Решение по backend-контракту:
  - `path` в `set_policy` это путь политики, один вызов на всю политику
  - `jsonData` в `set_policy` это строка
  - `metadata` в `set_policy` это строка пути из `Read_Path_GPT('...')`
  - `get_current_value` для `policyValue` возвращает строку JSON
  - состояние политики определяется по полю `state` в этом JSON
  - draft-режим не нужен

## 1. Цель изменений

Перевести ADMX-экран в `chain/js/app.js` с browser-local хранения на server-backed работу через `chain/js/API.js`, чтобы:

- текущее состояние политики читалось с backend
- изменения сохранялись в backend
- `localStorage` больше не участвовал в ADMX
- `Apply` действительно сохранял политику

## 2. Область изменений

### Входит в эту задачу

- `chain/js/app.js`
- при необходимости `chain/js/API.js`
- документация в `doc/`

### Не входит в эту задачу

- preferences storage (`shortcuts` и другие preference-шаблоны)
- `chain/css/*`, если не потребуется минимальный UI для loading/error
- логика `chain/gpo.js`, кроме использования как справочного контекста
- backend-реализация RPC

## 3. Текущее состояние системы

### 3.1. Что в `chain` отвечает за ADMX

- `chain/chain.js` подключает модуль `./gpo`
- `chain/gpo.js` регистрирует UI-сущность GPO и взаимодействие с FreeIPA
- `chain/js/API.js` содержит RPC-обертки:
  - `getPolicy(path)`
  - `getCurrentValue(nameGpt, target, path)`
  - `setPolicy(nameGpt, target, path, jsonData, metadata)`
  - `loadMainPolicy(path)`
- `chain/js/app.js` строит дерево политик, ADMX-формы и обрабатывает пользовательские действия

### 3.2. Что уже работает через API

- загрузка структуры политик через `API.loadMainPolicy()`
- получение `gpcfilesyspath` через `gpo.show`
- наличие RPC-методов для чтения и записи policy values

### 3.3. Что сейчас неправильно для ADMX

- `initAdmxStorage()` и связанный набор функций создают локальный ADMX-кэш
- `restorePersistedAdmxValues()` заполняет форму из `localStorage`
- `handleApply()` не вызывает backend, а сохраняет изменения только в браузер

## 4. Подтвержденный контракт backend

### 4.1. Вызов `set_policy`

Сигнатура фронта:

```js
API.setPolicy(nameGpt, target, path, jsonData, metadata)
```

Уточненный контракт:

- `nameGpt`: путь до GPO, берется из `gpcfilesyspath`
- `target`: `"Machine"` или `"User"`
- `path`: путь политики `admxTreePath`
- `jsonData`: строка
- `metadata`: строка из `Read_Path_GPT('...')`
- один вызов `set_policy` выполняется на всю политику

### 4.2. Источник `metadata`

`metadata` не берется напрямую из `policyValueEntry.metadata`.

Его нужно получать так:

1. вызываем `API.getPolicy(path)` для пути политики
2. в ответе ищем строку вида `Read_Path_GPT('Software\\...')`
3. извлекаем значение внутри кавычек
4. именно эта строка отправляется в `API.setPolicy(..., metadata)`

Пример:

```text
Read_Path_GPT('Software\\BaseALT\\Policies\\Control\\xdg-user-dirs')
```

Результат для отправки:

```text
Software\\BaseALT\\Policies\\Control\\xdg-user-dirs
```

### 4.3. Ответ `get_current_value`

Для `policyValue` backend возвращает строку JSON.

Фронт должен:

1. получить строку
2. распарсить ее через `JSON.parse`
3. взять `state`
4. по `state` определить:
   - `enabled`
   - `disabled`
   - `not-configured`

Ожидаемая минимальная форма:

```json
{
  "state": "disabled"
}
```

Если в JSON есть дополнительные поля со значениями контролов, они тоже должны быть использованы для заполнения формы.

## 5. Целевая архитектура

После миграции ADMX должен работать так:

1. структура дерева и формы загружается через `API.loadMainPolicy()`
2. при открытии конкретной политики клиент определяет:
   - `nameGpt`
   - `target`
   - `admxTreePath`
   - `metadata`
3. клиент вызывает `API.getCurrentValue(nameGpt, target, admxTreePath)`
4. ответ backend приводится к модели состояния формы
5. UI показывает реальные значения политики
6. при `Apply` UI собирает одно JSON-представление всей политики
7. это JSON-представление сериализуется в строку
8. вызывается `API.setPolicy(nameGpt, target, admxTreePath, jsonString, metadata)`
9. после успешного сохранения форма синхронизируется с server state

## 6. Обязательные изменения в `app.js`

### 6.1. Удалить ADMX LocalStorage

Из `chain/js/app.js` удалить ADMX-специфичный storage-код:

- `STORAGE_KEY = "admx"`
- `VALID_STATES`
- `validateAdmxEntry()`
- `validateAdmxSchema()`
- `initAdmxStorage()`
- `getAdmxFromLocalStorage()`
- `saveAdmxToLocalStorage()`
- `getAdmxEntriesByPaths()`
- `upsertAdmxEntries()`

Также удалить ADMX-специфичный вызов:

- `initAdmxStorage()` из инициализации приложения

Примечание:

- `safe-storage` и preference storage не трогать, если они используются вне ADMX

### 6.2. Убрать восстановление ADMX из localStorage

Удалить или перестать использовать:

- `resolveStoredState()`
- `restorePersistedAdmxValues()`
- `buildPersistedAdmxEntries()`

Замена:

- загрузка значений должна происходить из API

### 6.3. Добавить target в ADMX item

В `convertPolicyCategory()` каждый policy item должен явно содержать target:

```js
target: sectionClass
```

Ожидаемые значения:

- `"Machine"`
- `"User"`

Это обязательное поле для:

- `API.getCurrentValue()`
- `API.setPolicy()`

### 6.4. Устранить двойной `name_gpt`

Сейчас в `app.js` существует:

- переменная `name_gpt` на уровне модуля
- переменная `name_gpt` внутри `init()`

Это создает риск рассинхронизации.

Требование:

- оставить один источник истины для `name_gpt`
- все функции чтения и сохранения ADMX должны использовать именно его

Рекомендуемый вариант:

- хранить `name_gpt` в замыкании `init()` и передавать его в ADMX-рендер явно
- либо вынести в одно централизованное состояние рядом с `mainPolicy`

## 7. Новые функции, которые нужно добавить

### 7.1. Функция извлечения metadata для политики

Нужна отдельная функция, условно:

```js
async function resolveAdmxMetadata(admxTreePath)
```

Поведение:

1. вызвать `API.getPolicy(admxTreePath)`
2. обойти ответ
3. найти строку `Read_Path_GPT('...')`
4. извлечь и вернуть внутреннее значение

Результат:

- строка вида `Software\\BaseALT\\Policies\\...`
- либо `null`, если путь не найден

Требование:

- использовать существующую логику извлечения через regex как основу
- если структура ответа сложная, искать рекурсивно по строковым полям объекта

### 7.2. Функция загрузки текущего ADMX состояния из API

Нужна отдельная функция, условно:

```js
async function loadAdmxStateFromApi({ nameGpt, target, admxTreePath })
```

Поведение:

1. определить `metadata` для политики
2. вызвать `API.getCurrentValue(nameGpt, target, admxTreePath)`
3. если ответ строка, распарсить JSON
4. вернуть нормализованную модель состояния формы

Минимальный ожидаемый результат:

```js
{
  state: "enabled" | "disabled" | "not-configured",
  values: {}
}
```

Где `values`:

- объект значений для контролов формы
- ключи должны позволять сопоставить данные с `controlEntries`

### 7.3. Функция применения server state к форме

Нужна отдельная функция, условно:

```js
function applyAdmxApiState({ rootElement, apiState, controlEntries, policyValueEntry })
```

Поведение:

1. выставить `state`
2. выставить значения контролов
3. вызвать `syncControlsWithPolicyState(rootElement)`

Требование:

- не использовать `localStorage`
- не мутировать исходные `controlEntries`

### 7.4. Функция сборки payload для `setPolicy`

Нужна отдельная функция, условно:

```js
function buildAdmxPolicyPayload({ rootElement, controlEntries, policyValueEntry })
```

Поведение:

1. прочитать текущий state формы
2. прочитать значения всех контролов
3. собрать один объект всей политики
4. сериализовать его через `JSON.stringify`

Минимальная целевая форма:

```json
{
  "state": "enabled",
  "values": {
    "Software\\...\\Value1": "abc",
    "Software\\...\\Value2": 10
  }
}
```

Допускается иная форма JSON, если она соответствует ожиданиям backend, но она должна:

- описывать всю политику одним объектом
- быть сериализована в строку
- содержать `state`

## 8. Изменения в `renderAdmxTemplate()`

### 8.1. Инициализация формы

Текущая логика:

- строит форму
- читает persisted entries из `localStorage`
- восстанавливает значения

Новая логика:

1. построить форму на основе `policyData`
2. временно перевести форму в loading state
3. вызвать `loadAdmxStateFromApi(...)`
4. применить полученные значения
5. зафиксировать `initialFormSnapshot`

### 8.2. Loading state

Пока значения политики загружаются:

- `Apply` и `Cancel` должны быть неактивны
- контролы формы должны быть disabled
- допускается текстовый индикатор загрузки без отдельной стилизации

### 8.3. Ошибка загрузки

Если `API.getCurrentValue()` или чтение metadata завершились ошибкой:

- форма не должна silently показывать пустые локальные значения
- нужно показать ошибку в UI или через `console.error`
- `Apply` не должен позволять сохранять заведомо несинхронизированную форму

Минимальное требование:

- `console.error`
- отключенный `Apply`

## 9. Изменения в обработчике Apply

Текущая логика:

- собрать `admxEntries`
- сохранить их в `localStorage`
- обновить snapshot

Новая логика:

1. проверить, что есть:
   - `nameGpt`
   - `target`
   - `admxTreePath`
   - `metadata`
2. собрать payload через `buildAdmxPolicyPayload()`
3. вызвать:

```js
await API.setPolicy(nameGpt, target, admxTreePath, jsonString, metadata)
```

4. после успеха:
   - обновить `initialFormSnapshot`
   - выключить `Apply/Cancel`
   - при необходимости перечитать данные через `loadAdmxStateFromApi()`

5. при ошибке:
   - не менять `initialFormSnapshot`
   - оставить форму в текущем состоянии
   - показать ошибку

## 10. Правила сопоставления данных API и формы

### 10.1. Источник state

Источник состояния политики:

- JSON, возвращенный `get_current_value`
- поле `state`

Если значение отсутствует или JSON невалиден:

- использовать `not-configured`

### 10.2. Источник значений контролов

Предпочтительный источник:

- JSON из `get_current_value`

Сопоставление должно использовать уже имеющиеся поля:

- `controlEntries[*].policyPath`
- `controlEntries[*].storagePath`
- `metadata.valueName`

Приоритет ключей сопоставления:

1. `storagePath`
2. `policyPath`
3. `metadata.valueName`

### 10.3. Типизация контролов

Существующую логику типизации контролов сохранить:

- `boolean`
- `enum`
- `decimal`
- `text`

Требование:

- преобразование значения из API к контролу должно проходить через существующие `applyControlValue()` и `readControlValue()`, где это возможно

## 11. Изменения в `API.js`

Базово `API.js` уже достаточен.

Обязательных изменений нет, если:

- `getCurrentValue()` возвращает строку
- `setPolicy()` принимает строку `jsonData`

Допустимые улучшения:

- добавить краткие комментарии по контракту аргументов
- улучшить текст ошибок для ADMX-сценария

Но это не блокер задачи.

## 12. Нефункциональные требования

### 12.1. Совместимость

- не сломать существующую загрузку дерева политик
- не сломать preference templates
- не сломать `gpo.show` и получение `gpcfilesyspath`

### 12.2. Поддерживаемость

- новая логика чтения и сохранения ADMX должна быть вынесена в отдельные функции
- избегать смешивания RPC-логики и DOM-манипуляций в одном большом обработчике

### 12.3. Прозрачность ошибок

- ошибки чтения и сохранения должны логироваться
- состояние UI после ошибки должно быть предсказуемым

## 13. Пошаговый план реализации

### Этап 1. Подготовка модели данных

1. Убрать дублирование `name_gpt`
2. Добавить `target` в ADMX item
3. Подготовить функции:
   - `resolveAdmxMetadata()`
   - `loadAdmxStateFromApi()`
   - `applyAdmxApiState()`
   - `buildAdmxPolicyPayload()`

### Этап 2. Перевод чтения ADMX на API

1. Удалить чтение persisted entries из `localStorage`
2. В `renderAdmxTemplate()` загружать текущее значение через API
3. Заполнять форму из server response
4. Только после этого фиксировать initial snapshot

### Этап 3. Перевод сохранения ADMX на API

1. Удалить `upsertAdmxEntries()` из `Apply`
2. Добавить вызов `API.setPolicy()`
3. После успеха обновлять snapshot
4. Проверить `Cancel` после server sync

### Этап 4. Очистка legacy-кода

1. Удалить ADMX localStorage helpers
2. Удалить `initAdmxStorage()`
3. Удалить неиспользуемые ADMX-функции

## 14. Критерии приемки

Задача считается выполненной, если:

1. при открытии ADMX-политики форма не читает данные из `localStorage`
2. текущее состояние политики берется из `API.getCurrentValue()`
3. `state` формы определяется из JSON-поля `state`
4. `Apply` вызывает один `API.setPolicy()` на всю политику
5. в `setPolicy()` передаются:
   - корректный `nameGpt`
   - корректный `target`
   - `admxTreePath` как `path`
   - строка JSON как `jsonData`
   - строка из `Read_Path_GPT('...')` как `metadata`
6. после успешного `Apply` форма считается синхронизированной
7. ADMX-код больше не содержит активной логики `localStorage`

## 15. Риски

### Риск 1. Неоднозначная структура JSON от `get_current_value`

Если backend возвращает JSON с нестабильной структурой, сопоставление с контролами может потребовать отдельного адаптера.

### Риск 2. Поиск `Read_Path_GPT()` в ответе `getPolicy`

Если строка находится не в одном и том же поле, понадобится рекурсивный обход всех строковых значений объекта.

### Риск 3. Асинхронный рендер ADMX

`renderAdmxTemplate()` сейчас по сути синхронный. При переходе на API появится асинхронная загрузка значений, которую нужно аккуратно встроить без гонок при быстром переключении узлов.

### Риск 4. Уничтожение view во время запроса

Если пользователь переключился на другую политику до завершения `getCurrentValue()`, нельзя применять результат в уже уничтоженный DOM.

Требование:

- использовать существующий механизм cleanup
- перед применением результата проверять, что view еще актуален

## 16. Тестовые сценарии

### Сценарий 1. Открытие Machine ADMX политики

Ожидание:

- форма заполнилась данными backend
- `state` выставлен из JSON
- `Apply` изначально неактивен

### Сценарий 2. Открытие User ADMX политики

Ожидание:

- в `getCurrentValue()` уходит `target = "User"`
- форма корректно заполняется

### Сценарий 3. Изменение значения и Apply

Ожидание:

- вызывается один `setPolicy()`
- `jsonData` передан строкой
- `metadata` передан строкой extracted `Read_Path_GPT`

### Сценарий 4. Ошибка чтения

Ожидание:

- показывается ошибка
- форма не делает вид, что загрузила валидные данные из локального кеша

### Сценарий 5. Ошибка сохранения

Ожидание:

- `initialFormSnapshot` не обновляется
- `Apply` остается доступным для повторной попытки после исправления

### Сценарий 6. Отсутствие localStorage-следов

Ожидание:

- удаление/очистка `localStorage` не влияет на ADMX
- повторное открытие политики показывает server state

## 17. Итоговое решение

ADMX в `chain/js/app.js` переводится на server-first модель:

- структура политики приходит через `API.loadMainPolicy()`
- текущее значение политики читается через `API.getCurrentValue()`
- вся политика сохраняется одним вызовом `API.setPolicy()`
- `localStorage` полностью исключается из ADMX-контура

Это и является целевой спецификацией для дальнейшей реализации.
