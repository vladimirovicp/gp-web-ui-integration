# Отчет по ADMX LocalStorage и предложениям по переходу на API.js

## Цель

Разобрать, как в `chain/js/app.js` сейчас работает хранение ADMX-данных через `localStorage`, откуда данные берутся, куда они отправляются, и предложить схему отказа от `localStorage` в пользу `chain/js/API.js`.

## Что есть сейчас

### 1. Загрузка дерева политик уже идет через API.js

- `mainPolicyPromise = initializeMainPolicy(options.path || "/")` запускает загрузку основной политики в `chain/js/app.js:3586`.
- `initializeMainPolicy()` вызывает `API.loadMainPolicy(path || "/")` в `chain/js/app.js:3297-3300`.
- В `chain/js/API.js:67-68` `loadMainPolicy()` вызывает `getPolicy()`.
- В `chain/js/API.js:52-54` `getPolicy(path)` вызывает RPC `gpo.get_policy`.

Итог: структура ADMX-дерева, категории, политики, `metadata`, `header`, `policyData` уже приходят с сервера, а не из `localStorage`.

### 2. Для выбранного GPO уже получаем путь до файловой политики

- При инициализации `app.js`, если есть `options.policyName`, выполняется `rpc.command({ entity: "gpo", method: "show", ... })` в `chain/js/app.js:3566-3582`.
- Из ответа берется `gpcfilesyspath` и кладется в переменную `name_gpt` в `chain/js/app.js:3573-3575`.

Итог: клиент уже знает `name_gpt`, который нужен для `API.getCurrentValue(nameGpt, target, path)` и `API.setPolicy(nameGpt, target, path, jsonData, metadata)`.

### 3. ADMX-форма собирается из server-side policyData

- Элементы дерева ADMX создаются в `convertPolicyCategory()` в `chain/js/app.js:547-580`.
- Для каждой политики в item кладутся:
  - `policyKey`
  - `policyData`
  - `template: "admx"`
  - `admxTreePath`
- В `renderAdmxTemplate()` в `chain/js/app.js:1392-1402` идет разбор `item.policyData`.
- `normalizePolicyEntries()` в `chain/js/app.js:1022-1048` превращает `policyData` в:
  - `controlEntries`
  - `policyValueEntry`
- `resolvePolicyPath()` в `chain/js/app.js:1009-1020` и `extractStoragePathFromData()` в `chain/js/app.js:1002-1007` вычисляют пути значений.

Итог: UI ADMX уже строится на основании данных, пришедших через `get_policy`, а не на основании локального хранилища.

## Где используется localStorage

### 1. Безопасная обертка над localStorage

В `chain/js/app.js:887-926` реализованы:

- `getItemSafe()`
- `setItemSafe()`
- `ensureInitialized()`

### 2. ADMX-хранилище в localStorage

В `chain/js/app.js:928-989` реализован отдельный storage:

- `STORAGE_KEY = "admx"`
- `initAdmxStorage()`
- `getAdmxFromLocalStorage()`
- `saveAdmxToLocalStorage()`
- `getAdmxEntriesByPaths()`
- `upsertAdmxEntries()`

Формат записи:

- ключ верхнего уровня: `path`
- значение: объект вида:
  - `path`
  - `state`
  - `type`
  - `value`
  - `policyKey`
  - `policyTitle`
  - `admxTreePath`
  - `updatedAt`

### 3. Инициализация ADMX localStorage

- `initAdmxStorage()` вызывается при старте приложения в `chain/js/app.js:3585`.

### 4. Восстановление значений формы из localStorage

- В `renderAdmxTemplate()` в `chain/js/app.js:1400-1404` собирается список путей.
- Затем через `getAdmxEntriesByPaths()` поднимаются записи из `localStorage`.
- `restorePersistedAdmxValues()` в `chain/js/app.js:1317-1336` накладывает их на форму.

Итог: при открытии ADMX-политики пользователь видит не server-side текущее значение, а последнее локально сохраненное значение из браузера, если оно есть.

### 5. Отправка данных сейчас фактически не идет на сервер

- При нажатии `Apply` в `renderAdmxTemplate()` в `chain/js/app.js:1620-1644` собирается массив `admxEntries`.
- `buildPersistedAdmxEntries()` в `chain/js/app.js:1349-1391` формирует записи для сохранения.
- Дальше вызывается только `upsertAdmxEntries(admxEntries)`.

Итог: `Apply` сохраняет ADMX-данные только в `localStorage`. Вызова `API.setPolicy()` здесь нет.

## Как данные получаем и как "отправляем" сейчас

### Получаем

1. `API.loadMainPolicy()` -> `API.getPolicy()` -> RPC `gpo.get_policy`.
2. Из ответа строится дерево категорий и политик.
3. Для выбранной ADMX-политики из `policyData` получаем:
   - описание политики
   - типы полей
   - `metadata`
   - `policyValueEntry`
   - вычисленные `policyPath` и `storagePath`
4. Дополнительно поверх этого UI подтягивает локальный слепок из `localStorage`.

### Отправляем

Сейчас реальной отправки ADMX-изменений на сервер из `app.js` нет.

Есть только:

1. сбор данных формы в `buildPersistedAdmxEntries()`
2. запись результата в `localStorage` через `upsertAdmxEntries()`

## Проблемы текущего подхода

### 1. localStorage не является источником истины

Сейчас фактическое состояние политики на сервере и состояние, которое видит пользователь в браузере, могут расходиться.

Примеры:

- политику изменили из другого клиента
- пользователь открыл другой браузер
- пользователь очистил браузерные данные
- один и тот же GPO открыт у нескольких администраторов

### 2. Нет настоящего чтения текущего значения политики

Хотя `API.getCurrentValue()` уже реализован в `chain/js/API.js:57-60`, в рабочем потоке ADMX он не используется. Значит форма не синхронизируется с реальным значением на сервере.

### 3. Apply создает ложное ощущение сохранения

По UX кнопка `Apply` выглядит как сохранение политики, но фактически сохраняет только browser-local состояние.

### 4. Локальные данные не привязаны жестко к конкретному GPO

В записи хранится `path`, `policyKey`, `policyTitle`, `admxTreePath`, но storage-ключ общий: `admx`. Если одинаковые пути встретятся между разными GPO, возможны конфликты или некорректное восстановление.

### 5. Дублируется модель данных

Сейчас приложение поддерживает сразу две модели:

- server-side модель через `get_policy`
- browser-side модель через `localStorage`

Это усложняет логику и повышает риск расхождений.

## Что уже есть для перехода на API.js

### API.js уже покрывает нужные операции

В `chain/js/API.js` уже есть:

- `getPolicy(path)` для загрузки структуры политики
- `getCurrentValue(nameGpt, target, path)` для чтения текущего значения конкретного policy path
- `setPolicy(nameGpt, target, path, jsonData, metadata)` для сохранения политики

### Данные для вызова API почти полностью уже собраны в app.js

Для вызова API уже доступны или могут быть вычислены:

- `nameGpt`
  - уже берется из `gpcfilesyspath` в `chain/js/app.js:3573-3575`
- `target`
  - можно определить из корня дерева: `Machine` или `User`
  - сейчас для ADMX item это удобнее всего сохранять прямо в item при `convertPolicyCategory()`
- `path`
  - уже вычисляется как `policyPath` / `storagePath` в `normalizePolicyEntries()`
- `jsonData`
  - можно строить из текущего состояния формы
- `metadata`
  - уже приходит в `policyData.*.metadata`

## Предложения по отказу от localStorage

### Вариант 1. Полностью убрать localStorage для ADMX

Это базовый и наиболее чистый вариант.

Что сделать:

1. Удалить ADMX storage-функции:
   - `initAdmxStorage()`
   - `getAdmxFromLocalStorage()`
   - `saveAdmxToLocalStorage()`
   - `getAdmxEntriesByPaths()`
   - `upsertAdmxEntries()`
2. Удалить вызов `initAdmxStorage()` из инициализации.
3. В `renderAdmxTemplate()` вместо `getAdmxEntriesByPaths()` вызывать загрузку текущих значений через `API.getCurrentValue()`.
4. В `handleApply()` вместо `upsertAdmxEntries()` вызывать `API.setPolicy()`.

Плюсы:

- один источник истины
- корректная работа между браузерами и пользователями
- кнопка `Apply` начинает реально сохранять

Минусы:

- нужно добавить асинхронную загрузку значений формы
- нужно договориться о формате `jsonData` и `metadata` для `set_policy`

### Вариант 2. Оставить localStorage только как временный draft

Это компромиссный вариант, если нужен черновик несохраненных изменений.

Что сделать:

1. Основное чтение делать только из `API.getCurrentValue()`.
2. `localStorage` использовать только как draft, явно отделив его от сохраненной политики.
3. В UI различать:
   - server value
   - draft value
4. После успешного `API.setPolicy()` очищать draft.

Плюсы:

- можно не потерять несохраненные правки
- миграция мягче

Минусы:

- логика сложнее
- остается риск путаницы между draft и реальным состоянием

### Рекомендация

Рекомендую идти по варианту 1: полностью убрать `localStorage` из ADMX-контура.

Причина: для административных политик особенно важно, чтобы UI всегда показывал и изменял именно серверное состояние, а не локальный браузерный кэш.

## Практический план миграции

### Шаг 1. Явно сохранить target в item ADMX

Сейчас `convertPolicyCategory()` получает `sectionClass`, но не кладет его в элемент политики.

Предложение:

- при формировании item в `chain/js/app.js:570-579` добавить, например:
  - `target: sectionClass`
  - или `header: { class: sectionClass }`

Это упростит вызовы `API.getCurrentValue(nameGpt, item.target, path)`.

### Шаг 2. Сделать загрузку текущих значений через API.getCurrentValue()

Для ADMX-экрана после `normalizePolicyEntries()`:

1. взять `policyValueEntry?.policyPath`
2. взять `controlEntries[*].policyPath`
3. для каждого пути запросить `API.getCurrentValue(name_gpt, target, path)`
4. результатом заполнить форму через существующие:
   - `setSelectedAdmxState()`
   - `applyControlValue()`
   - `syncControlsWithPolicyState()`

Важно:

- `policyValueEntry` лучше использовать для определения текущего `state`
- остальные `controlEntries` использовать для заполнения конкретных полей

### Шаг 3. Убрать restore из localStorage

В `renderAdmxTemplate()` убрать:

- `getAdmxEntriesByPaths(...)`
- `restorePersistedAdmxValues(...)`

Вместо этого:

- добавить асинхронную функцию вроде `loadAdmxValuesFromApi()`
- показывать loading state, пока значения не подгружены

### Шаг 4. Заменить Apply на API.setPolicy()

Сейчас `handleApply()`:

- собирает `admxEntries`
- пишет их в `localStorage`

Нужно заменить на:

1. собрать server payload из формы
2. вызвать `API.setPolicy(name_gpt, target, path, jsonData, metadata)`
3. после успеха:
   - обновить `initialFormSnapshot`
   - снять активность с `Apply/Cancel`
   - при необходимости повторно прочитать значения через `API.getCurrentValue()`

### Шаг 5. Удалить ADMX localStorage-код

После перевода чтения и записи:

- удалить `STORAGE_KEY = "admx"` и все функции рядом
- удалить `initAdmxStorage()` из старта приложения

## Какой payload логично готовить для setPolicy

Точный формат зависит от backend-реализации `gpo.set_policy`, но с точки зрения фронта можно собирать модель такого вида:

```json
{
  "state": "enabled",
  "values": [
    {
      "path": "Software\\...\\ValueName",
      "type": "text",
      "value": "example"
    }
  ]
}
```

Либо вызывать `setPolicy()` по одному пути:

- отдельно для `policyValueEntry`
- отдельно для каждого control entry

Предпочтительнее сначала уточнить backend contract, потому что сигнатура `setPolicy(nameGpt, target, path, jsonData, metadata)` предполагает, что:

- либо `path` это корневой путь политики, а `jsonData` содержит все дочерние значения
- либо `path` это конкретный registry path/value path, и тогда нужен набор последовательных вызовов

## Минимальный технический сценарий замены

Если нужен самый короткий путь без большого рефакторинга:

1. оставить текущий UI рендеринг как есть
2. убрать восстановление из `localStorage`
3. при открытии ADMX загрузить значения через `API.getCurrentValue()`
4. при `Apply` вызвать `API.setPolicy()`
5. только после успешного ответа обновлять snapshot формы

Такой путь даст быстрый выигрыш без перестройки всего компонента.

## Что стоит уточнить перед реализацией

### 1. Контракт backend для set_policy

Нужно точно понять:

- что именно ожидается в `jsonData`
- что именно должно приходить в `metadata`
- один вызов нужен на всю политику или на каждое значение

### 2. Формат ответа get_current_value

Нужно проверить:

- что возвращается для `policyValue`
- как отличить `enabled`, `disabled`, `not-configured`
- как маппить ответ на существующие типы контролов: `boolean`, `enum`, `decimal`, `text`

### 3. Нужен ли режим draft

Если заказчик хочет именно черновики между открытиями страницы, тогда `localStorage` можно оставить, но уже как отдельный опциональный draft-слой, а не как основное хранилище.

## Вывод

Сейчас `localStorage` в ADMX нужен только для локального сохранения состояния формы в браузере. Реальная модель политик уже загружается через `API.js`, но при этом:

- текущие значения политики с сервера не читаются в рабочем потоке ADMX
- `Apply` не сохраняет на сервер

Поэтому `localStorage` можно и логично вырезать из ADMX-контура.

Лучший путь:

1. использовать `API.loadMainPolicy()` только для структуры политики
2. использовать `API.getCurrentValue()` для заполнения текущих значений
3. использовать `API.setPolicy()` для сохранения
4. удалить ADMX `localStorage` как источник состояния

Это сделает поведение ADMX предсказуемым, серверно-ориентированным и корректным для административного интерфейса.
